Hetzner har intet FreeBSD-image, og deres ISO-bibliotek stopper ved 15.0. Du kan stadig få enhver release ind på maskinen, uden manuel indgriben, på omkring en time.

Maskinen kører AthletOS, en træningsapp jeg bygger. Foruddefinerede programmer, sessionslogning og tracking.

— Jeg valgte FreeBSD for ZFS boot environments og jails, så en dårlig deploy er et rollback i stedet for en incident.

Her er hele proceduren, i rækkefølge, inklusiv de ting der gik galt, og hvad der løste dem. Jeg brugte FreeBSD's egen ISO fremfor et færdigbygget image, så tjeksummen kan verificeres op mod projektets manifest.

1. Opret serveren

En CX23 giver 2 vCPU og 4 GB, hvilket er rigeligt. Firewall først, så maskinen.

1-create-server.sh
hcloud firewall create --name athletos
for p in 22 80 443; do
  hcloud firewall add-rule athletos --direction in --protocol tcp \
    --port $p --source-ips 0.0.0.0/0 --source-ips ::/0
done

hcloud server create --name athletos --type cx23 --location hel1 \
  --image debian-12 --ssh-key my-key --firewall athletos

Imaget er til engangsbrug. Det findes kun for at få serveren til at boote overhovedet.

2. Boot i rescue

2-rescue.sh
hcloud server enable-rescue athletos --ssh-key my-key
hcloud server reset athletos

ssh root@<ip>          # linux rescue, ~1.9GB overlay in RAM

3. Hent og verificér ISO'en

Tag bootonly, ikke disc1. Rescue-roden er et lille RAM-overlay, og en 1,3 GB ISO plus udpakning plus genopbygning kan ikke være der.

3-fetch-iso.sh
B=https://download.freebsd.org/releases/amd64/amd64/ISO-IMAGES/15.1
I=FreeBSD-15.1-RELEASE-amd64-bootonly.iso

curl -fsSL -o CHECKSUM $B/CHECKSUM.SHA256-FreeBSD-15.1-RELEASE-amd64
curl -fsSL -o $I $B/$I

E=$(grep -E "\($I\)" CHECKSUM | sed 's/.*= //')
A=$(sha256sum $I | cut -d' ' -f1)
[ "$E" = "$A" ] && echo "verified" || echo "STOP"

4. Tilpas ISO'en

Tre ændringer: en seriel konsol så vi kan følge med, prompten der ellers ville blokere for evigt, og netværket som en scriptet installation aldrig selv konfigurerer.

4-remaster.sh
apt-get install -y xorriso qemu-system-x86

mkdir -p isowork isomnt
mount -o loop,ro $I isomnt && cp -a isomnt/. isowork/ && umount isomnt
chmod -R u+w isowork

# append, never replace: the original carries vfs.root.mountfrom
cat >> isowork/boot/loader.conf <<'EOF'
console="comconsole"
comconsole_speed="115200"
boot_serial="YES"
vfs.root.mountfrom="cd9660:/dev/iso9660/FREEBSD_INSTALL"
EOF

# the serial path asks for a terminal type with an unconditional read
sed -i 's/^\([[:space:]]*\)read TERM$/\1:/' \
    isowork/usr/libexec/bsdinstall/startbsdinstall

# a scripted install never configures the network
sed -i 's|^mkdir /tmp/bsdinstall_etc$|&\nifconfig vtnet0 inet 10.0.2.15/24 up\nroute add default 10.0.2.2\necho "nameserver 10.0.2.3" > /tmp/bsdinstall_etc/resolv.conf|' \
    isowork/etc/rc.local

Hvad der gik galt

Jeg overskrev loader.conf i stedet for at tilføje til den, hvilket smed vfs.root.mountfrom væk og efterlod maskinen ved en mountroot-prompt.

Derefter hang den ved Console type [vt100]:, fordi den read kører, før scriptet overhovedet bliver fundet.

Derefter døde distfetch på DNS, fordi den interaktive sti eksporterer BSDINSTALL_CONFIGCURRENT, mens den scriptede sti ikke gør.

5. Skriv det automatiske installationsscript

isowork/etc/installerconfig
PARTITIONS=DEFAULT
DISTRIBUTIONS="kernel.txz base.txz"
export ZFSBOOT_VDEV_TYPE=stripe
export ZFSBOOT_DISKS=vtbd0
export ZFSBOOT_SWAP_SIZE=2g
export ZFSBOOT_CONFIRM_LAYOUT=0
export nonInteractive=YES
export BSDINSTALL_DISTSITE=http://10.0.2.2:8000

#!/bin/sh
sysrc hostname="athletos"
sysrc ifconfig_vtnet0="DHCP"
sysrc sshd_enable="YES"
sysrc zfs_enable="YES"

# ARC takes half of RAM by default. On a 4GB box that is 2GB it does not
# need, and it turns up later looking like a database problem.
echo 'vfs.zfs.arc_max="512M"' >> /boot/loader.conf

mkdir -p /root/.ssh && chmod 700 /root/.ssh
echo 'ssh-ed25519 AAAA... you@host' > /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys

10.0.2.2 er QEMU's host-adresse. At servere distributionssættene fra rescue springer DNS helt over og er hurtigere end at hente dem to gange.

5-serve-dist.sh
mkdir -p dist && cd dist
B=https://download.freebsd.org/releases/amd64/15.1-RELEASE
for f in MANIFEST base.txz kernel.txz; do curl -fsSL -O $B/$f; done

while read -r name sha rest; do
  [ -f "$name" ] || continue
  [ "$(sha256sum "$name" | cut -d' ' -f1)" = "$sha" ] && echo "OK $name"
done < MANIFEST

setsid nohup python3 -m http.server 8000 >/dev/null 2>&1 &

Tip: lad den server køre. Installeren henter fra den i trin 7, ikke nu.

6. Byg ISO'en og ryd disken

Slet kilde-ISO'en før du bygger, ellers løber du tør for plads i overlayet.

6-build-and-wipe.sh
rm -f $I
xorriso -as mkisofs -r -V FREEBSD_INSTALL -b boot/cdboot -no-emul-boot \
        -o athletos-install.iso isowork/
rm -rf isowork

# zfs labels sit at both ends of the device, so wipefs alone is not enough
SECTORS=$(blockdev --getsz /dev/sda)
MIB=$(( SECTORS / 2048 ))
wipefs -a /dev/sda
dd if=/dev/zero of=/dev/sda bs=1M count=64 conv=fsync
dd if=/dev/zero of=/dev/sda bs=1M seek=$(( MIB - 64 )) count=64 conv=fsync

Hvad der gik galt

Et tidligere forsøg kom langt nok til at oprette en zroot-pool, før det fejlede.

Næste kørsel fandt den og stoppede for at spørge om et andet pool-navn, hvilket er endnu en dialog, der ikke er nogen til at besvare. Ryd begge ender mellem forsøgene.

7. Kør installeren under QEMU

Hetzner Cloud har ingen nested virtualisation, så der er ingen /dev/kvm, og det her kører under TCG-emulering. Det tager cirka en halv time. Der er ikke andet at gøre end at følge loggen.

7-install.sh
qemu-system-x86_64 -accel tcg,thread=multi -m 2048 -smp 2 \
  -drive file=/dev/sda,format=raw,if=virtio,cache=writeback \
  -cdrom athletos-install.iso -boot d \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \
  -display none -monitor none -serial file:/root/install.log -daemonize

grep -aoE "Running installation step: [a-z]+" /root/install.log | uniq
# zfsboot mount distfetch checksum distextract bootconfig config
# entropy umount script

Dræb QEMU, så snart script-trinnet er færdigt, ellers genstarter den direkte tilbage i installeren.

8. Boot den og ret fstab

8-boot.sh
hcloud server disable-rescue athletos
hcloud server reset athletos

ssh root@<ip>

# the installer ran under qemu virtio (vtbd0), hetzner presents da0.
# the pool is fine because zfs scans devices. swap is not.
printf '/dev/gpt/swap0\tnone\tswap\tsw\t0\t0\n' > /etc/fstab
swapon -a

Hvad der gik galt

Den genererede fstab pegede på /dev/vtbd0p2, som ikke findes på den rigtige maskine.

Den bootede uden swap og sagde ingenting om det. Referér til den via GPT-label, så bliver enhedsnavnet ligegyldigt.

Under belastning

Jeg målte dette fra en separat Hetzner VPS i det samme datacenter, hel1, mod en kontrolmaskine: en identisk CX23 med Ubuntu 24.04, den samme Caddy 2.11.4 der serverer byte-identiske filer, med et tilsvarende ECDSA P-256-certifikat. vegeta, en frisk TCP- og TLS-forbindelse pr. forespørgsel, hvilket er det en crawler gør og det en browser aldrig gør.

9-load.sh
vegeta attack -targets targets.txt -rate 500 -duration 10s \
       -keepalive=false -timeout 20s | vegeta report

# freebsd   100/s  4.9ms   250/s  4.7ms   500/s  4.0ms   mean
# ubuntu    100/s  5.7ms   250/s  5.0ms   500/s  5.2ms   mean

Ved 100, 250 og 500 friske forbindelser i sekundet leverede begge maskiner den fulde belastning med 100% succes, og FreeBSD-maskinen var hurtigst ved hvert eneste trin.

Kryptografien er heller ikke flaskehalsen.

openssl speed ecdsap256
# sign/s
#  37920   this box (epyc, one core)
#  32614   ubuntu control (xeon, one core)

EPYC'en signerer 16% hurtigere end kontrolmaskinens Xeon, hvilket er værd at nævne, fordi det betyder, at hardwaren favoriserer FreeBSD-maskinen og ikke omvendt. Mod 500 forbindelser i sekundet giver 37.920 signaturer cirka 75x luft op til loftet. Hvad end loftet er, er det ikke asymmetrisk kryptografi.

To ting jeg ikke fik fastslået

Over 500/s var målingerne ikke reproducerbare. En ren kørsel ved 1000/s havde FreeBSD på 497/s og Ubuntu-kontrollen på 999/s. En senere kørsel gav 179/s ved 1000/s og derefter 566/s ved 1500/s — højere belastning gav højere throughput, hvilket ikke er en egenskab en server kan have. Det er den enlige load-generator, der akkumulerer TIME_WAIT mellem kørslerne. Et reelt svar kræver flere generatorer.

Et tidligere forsøg målte fra en Windows-bærbar over det offentlige internet og fik 50-100 forbindelser i sekundet. Det var fem til ti gange for lavt, og årsagen var udtømning af ephemeral ports på klienten. Den første måling var forkert, og den var forkert på en måde, der producerede en selvsikker og fuldstændig forkert forklaring.

Én hypotese døde undervejs. FreeBSD's kern.ipc.soacceptqueue er 128 og Ubuntus net.core.somaxconn er 4096, så listen-backloggen adskiller sig med 32x, hvilket lignede den oplagte årsag og holdt til regnestykket. Jeg satte kontrolmaskinen til 128, genstartede Caddy så listeneren tog den nye værdi, og den leverede stadig 999,9/s. Afkræftet.

Det efterlader pf, som viderestiller 443 til Caddys høje port, som den utestede mistænkte. Utestet fordi den høje port ikke kan nås udefra, så der var ingen måde at omgå viderestillingen og sammenligne op imod den.

De samme trin virker for enhver release. Skift versionen i trin 3, og resten følger med.

Hver eneste kommando ovenfor er kørt mod en rigtig CX23 i hel1.
