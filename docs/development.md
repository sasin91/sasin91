# Developing sasin91.xyz

The site is generated by a small Rust binary from [Djot](https://djot.net/)
content under `content/`. Output goes to `public/`, which is disposable and
regenerated on every build.

`mise.toml` pins the toolchain (Rust stable, Node 22, watchexec) and wraps the
commands below as tasks: `mise install` once, then `mise run serve`,
`mise run dev` or `mise run check`. Nothing requires mise; the cargo commands
are the same either way.

## Build

```sh
cargo run --release      # writes ./public
```

## Write

```sh
cargo run --release -- serve        # build, then serve at http://localhost:8000
cargo run --release -- serve 8080   # another port
```

To rebuild and restart on every change (`cargo install watchexec-cli`, or
`mise run dev` which does exactly this):

```sh
watchexec --restart --exts dj,html,css,rs,toml,mjs -- cargo run --release -- serve
```

`serve` (`src/serve.rs`) is a small standard-library server, localhost only.
It resolves URLs like the live Caddy config (`try_files {path} {path}/
{path}/index.html`), so `/blog` answers with a 308 to `/blog/` here too, and it
sends `Cache-Control: no-cache` so an edited stylesheet is never served stale.
It reads each file per request and never holds `public/` open, so a rebuild
can delete and recreate the directory while it runs.

On Windows, a build fails with "removing public/" if anything else has the
directory open: an Explorer window showing it, or a shell or another server
whose working directory is inside it. Close that and build again.

Pages link their assets root-absolutely (e.g. `/site.<hash>.css`, a hash that
changes with every stylesheet edit), so `public/` has to be the document root.
Any other static server works too, as long as it serves `public/` as `/`, e.g.
`python -m http.server 8000 --directory public`.

A post is one `.dj` file under `content/blog/` with a `+++` TOML header. The
`path` key is the URL, and is deliberately not derived from the filename — this
is what keeps `/blog/trongate/mx-transition` nested rather than flattened.

The AI article at `/blog/ai/` is different: it is assembled from knowledge nodes
under `content/ai/`, with a timeline and an in-browser Ask view generated from
the same nodes. See [knowledge-nodes.md](knowledge-nodes.md) for how to add,
edit, reorder and link nodes.

## Checks

```sh
cargo fmt --check
cargo clippy -- -D warnings
cargo test
cargo run --release && node --test js/retrieval.test.mjs   # the Ask view's browser code
```

The JavaScript tests use Node's built-in test runner (Node 22 or later); there
is no `package.json` and nothing to install.

## Deploy

Pushing to `main` builds the site in CI and rsyncs it to the FreeBSD box.
See [deploy.md](deploy.md).
